# FCM Infrastructure Runbook

Operator-facing notes for provisioning and maintaining FCM's managed cloud
services via Terraform. Story 1-5 establishes the IaC surface; Story 1-6 wires
the CI pipeline that runs `terraform plan` on every infra PR.

## Layout

The Terraform code lives at `infra/terraform/`:

```
infra/terraform/
├── modules/
│   ├── postgres/          # RDS Postgres 15+
│   ├── redis/             # ElastiCache Redis 7+
│   ├── object_storage/    # S3 evidence bucket
│   └── secrets/           # Secrets Manager entries
└── envs/
    ├── dev/
    ├── staging/
    └── prod/
```

Each environment composes all four modules and writes the resulting
connection strings into Secrets Manager. The application reads them at
runtime via the standard AWS Secrets Manager SDK (wired in EPIC-1.9 secrets
management).

## State isolation (AC3)

Every environment has its own backend bucket and lock table:

| Env | State bucket | State key | Lock table |
|---|---|---|---|
| dev | `fcm-tf-state-dev` | `fcm/dev.tfstate` | `fcm-tf-locks-dev` |
| staging | `fcm-tf-state-staging` | `fcm/staging.tfstate` | `fcm-tf-locks-staging` |
| prod | `fcm-tf-state-prod` | `fcm/prod.tfstate` | `fcm-tf-locks-prod` |

These buckets and tables are provisioned **out-of-band** by an operator with
elevated permissions, then never touched again. Recipe in the next section.

## One-time bootstrap (per AWS account)

```bash
# Create the state bucket and lock table for an environment.
# Repeat for staging and prod, substituting the env name.
ENV=dev
AWS_REGION=us-east-1

aws s3api create-bucket \
  --bucket fcm-tf-state-${ENV} \
  --region ${AWS_REGION} \
  --create-bucket-configuration LocationConstraint=${AWS_REGION}

aws s3api put-bucket-versioning \
  --bucket fcm-tf-state-${ENV} \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption \
  --bucket fcm-tf-state-${ENV} \
  --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'

aws dynamodb create-table \
  --table-name fcm-tf-locks-${ENV} \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST \
  --region ${AWS_REGION}
```

After bootstrap, the IaC pipeline can take over.

## Provisioning an environment

```bash
cd infra/terraform/envs/dev   # or staging | prod

# Initialize provider plugins and backend connection (run once per machine)
terraform init

# Preview changes
terraform plan

# Apply (operator-only; CI does not apply)
terraform apply
```

Provisioning emits four Secrets Manager entries per environment:

| Suffix | Secret name | Consumer |
|---|---|---|
| `database_url` | `fcm/<env>/database_url` | API + worker (Prisma) |
| `redis_url` | `fcm/<env>/redis_url` | API + worker (BullMQ) |
| `s3_bucket` | `fcm/<env>/s3_bucket` | API (pre-signed URLs) |
| `s3_region` | `fcm/<env>/s3_region` | API (pre-signed URLs) |

## CI guarantees (AC4)

A `terraform plan` job runs against every PR that touches `infra/terraform/`.
The job uses read-only AWS credentials and writes the plan output to the PR
as a comment. The workflow file itself lands with Story 1-6 (Kubernetes + CI
manifests); Story 1-5 ships the IaC surface that workflow targets.

## Operational notes

- **Backups (Arch §12.5):** Postgres backup retention is 7 days in dev, 14 in
  staging, 30 in prod. Object storage versioning is on by default; noncurrent
  versions tier to S3 Standard-IA at 90 days and expire at 7 years (audit horizon).
- **Deletion protection:**
  - **Postgres:** `deletion_protection = true` on staging and prod. Operators
    must explicitly toggle this off in Terraform before destroy works.
  - **Evidence bucket (prod):** `force_destroy = false` so a non-empty bucket
    refuses `terraform destroy` until manually emptied. Combined with versioning
    and per-env state isolation, this is the practical "no-one-line-oops" safety
    net. Terraform's `lifecycle { prevent_destroy }` cannot be parametrized from
    a variable so it is intentionally not used.
- **Secrets rotation:** Postgres master password is generated by Terraform at
  apply time, stored once in Secrets Manager as `fcm/<env>/database_url`, and
  the resource's `lifecycle.ignore_changes = [password]` ensures Terraform will
  not revert future rotations. The rotation Lambda itself ships in a later
  operational story; until then the password remains static (defer).
- **Auto-minor-version upgrade:** dev/staging accept AWS-driven minor Postgres
  bumps in the maintenance window; **prod has `auto_minor_version_upgrade = false`**
  and patches through a deliberate Terraform PR. The module also
  `ignore_changes = [engine_version]` so a non-prod auto-bump doesn't cause
  Terraform to plan a downgrade.
- **Application connection:** the application connects to Postgres via a
  **less-privileged role** (not the master user). The role is created
  out-of-band by an operator running a SQL bootstrap script (see EPIC-2 for
  the SQL to grant `SELECT/INSERT/UPDATE/DELETE` + RLS bypass). The application
  reads the live `database_url` secret at runtime — Terraform does NOT emit a
  pre-built connection string from the postgres module because any IaC-time URL
  would go stale at first rotation.
- **State-bucket access:** the bootstrap recipe above creates the state bucket
  with versioning + SSE-S3. **Before exposing the bucket to CI or additional
  operators, apply a bucket policy that scopes `s3:GetObject`/`s3:PutObject`
  to a specific `fcm-terraform-runner` IAM role + named operator roles.** The
  state file contains `random_password` plaintext for Postgres + Redis AUTH;
  any reader of the state bucket effectively has root on the data plane. A
  hardening pass (CMK on the state bucket, deny-all default policy) is tracked
  in `_bmad-output/implementation-artifacts/deferred-work.md`.
- **VPC / network isolation:** the postgres / redis modules accept
  `vpc_security_group_ids`, `db_subnet_group_name`, `subnet_group_name`, and
  `security_group_ids`. **They default to empty/null, which means RDS and
  ElastiCache fall back to the default VPC's default security group on first
  apply.** This is acceptable only for an initial smoke-test bring-up; before
  any real data lands, an operator must provision a dedicated VPC (private
  subnets, app-tier SG, database-tier SG) and pass its IDs into the modules
  from `envs/<env>/main.tf`. A dedicated `modules/network/` is tracked in
  deferred-work.md.
- **KMS keys:** Postgres / Redis / S3 use AWS-managed default keys for
  encryption-at-rest. Upgrading to per-app CMKs (with scoped key policies and
  rotation) is tracked in deferred-work.md.
- **S3 access logging:** disabled by default in the module; staging/prod
  callers should wire `access_log_bucket` to a separate log bucket once it
  exists. Until then, CloudTrail S3 data events (configured at the account
  level) are the only audit trail for evidence-bucket reads/writes.
- **Disaster recovery:** Arch §12.5 targets RPO ≤ 15 min, RTO < 2h. The IaC
  here supports those targets via daily snapshots + PITR + S3 versioning; the
  drill that actually exercises restore is Story E16.5.
